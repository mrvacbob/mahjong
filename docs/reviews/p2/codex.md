# Phase 2 cross-review · codex

## Scope and verification

I reviewed the Opus and Agy entries for Swift, Mercury, Python, and Haskell, including their source, designs, and working logs. The Mercury entries were absent from the main checkout, so I read the corresponding directories under `../wt/opus` and `../wt/agy` and ran their existing binaries. I did not read the Codex implementations or their logs, other reviewers’ files, the oracle or generators, or the held-back cases. I used the coordinator’s measurements for timing and held-back results. I inspected the build scripts, dependencies, input paths, and rule tables. I found no hard-coded corpus answers, corpus-derived tables, runtime data-file reads, or request-ID special cases in the eight entries. The shape tables are computed from tile counts and the fixed scoring tables encode the written rules.

I reran the public corpus and got 12,434/12,434 for each entry. The Python and Haskell build scripts completed. The Swift build scripts needed an in-tree module cache and a way around SwiftPM’s nested sandbox. They linked release executables, then failed at debug-symbol generation under the workspace permissions. I tested the linked release executables. I did not rebuild the external Mercury worktrees. The coordinator’s held-back set had no `legal` cases.

## Part A · Representatives

### Swift · keep Agy

| Rule | Opus | Agy |
|---|---|---|
| Pinfu | `Yaku(.pinfu, closed: 1, open: nil) { $0.isPinfuShape },` in `Yaku.swift`. The property in `Reading.swift` checks menzen, four runs, ryanmen and a non-value pair. | `YakuRule(name: "pinfu", closedHan: 1, openHan: 0) { ctx, h in` in `Score.swift`, then `guard wait == .ryanmen else { return false }`, an all-sequences guard and the value-pair check in the same closure. |
| Pinfu tsumo fu | `if r.isPinfuShape { return r.context.tsumo ? 20 : 30 }` in `Score.swift` reuses the predicate and also resolves closed pinfu ron. | `if hasPinfu && ctx.by == .tsumo {` followed by `return 20` in `Score.swift`. The ordinary fu path handles ron. |
| Riichi ankan | `guard k == drawn.kind else { continue }` and `guard before == now else { continue }` in `Legal.swift`. | `if req.wall >= 1 && req.kans < 4 && fullHand.counts[drawn.kind] == 4 {` and `return waitsBefore == waitsAfter` in `Legal.swift`. |

Both have distinct kind and physical-tile types, an input meld type, concealed decomposition groups, and a separate scoring interpretation with resolved openness. Both model legal triggers with associated-value enums. Opus’s `Reading` and named yaku enum make its score code easier to navigate. Its kuikae helper takes the two kinds from hand, checks adjacency, and uses bounded offsets to find the other end. Agy shares a helper between post-call discards and chi generation, using the chi base and the called rank to identify the far end. Both express kuikae once for chi. Agy’s indexed counts, `InlineArray` suit profiles and red mask are idiomatic value-type optimization, although explicit conversions and index loops make them more expensive to audit. Opus’s `HandSet` and Agy’s `ResolvedSet` both represent effective concealment after ron with a flag, and neither encodes every valid set/rank combination in the type.

**Valid failing request for Opus**, in a fresh process:

```text
probe legal hand=3456666999m789p melds=- draw=9m riichi=1
```

Expected and observed in the other seven entries: `probe actions=ankan:9m,discard:9m`. Opus returned `probe actions=discard:9m`. Before the draw, the structural waits are 3m (33 + 456 + 666) and a fifth 6m (345 + 666 + 66), alongside 999m and 789p. Moving the 9m triplet into the kan keeps both waits. The live `waits` operation correctly lists only 3m on both sides. Opus’s `structuralWaits` tests fifth copies through shanten, but `states` uses `let key = a.reduce(runs ? 1 : 2) { $0 * 5 + $1 }`. A count of five aliases a zero with a carry into the preceding count. Agy uses complete-hand recognition for structural tenpai waits, with no packed key in that path. The probe is significant because riichi is legal on the live 3m wait.

Both Swift executables also trapped on the extreme-honba input below. That is an input-boundary failure outside realistic game state. Agy’s log provides an initial clean compile and a concrete five-case kokushi correction, alongside conversion and hashing friction. Its design’s summary of kokushi still omits the corrected all-yaochu count. Opus records its nested closure error, `@Sendable` and main-actor diagnostics, checked release choice, and clean first corpus run. Both logs look plausible and identify different kinds of friction. Neither proves when the entries were logged.

**Before judging:** keep Agy’s distinct structural completion path, add the riichi-ankan regression, use typed yaku identifiers, split interpretation/payment from the long rule file, and validate or check arithmetic at the protocol boundary. Make the legal-action API return typed actions before formatting strings.

### Mercury · keep Opus

| Rule | Opus | Agy |
|---|---|---|
| Pinfu | `pinfu(C, standard(P, Ms, ryanmen)) :-`, with `C ^ closed = yes`, an all-runs test, and `not is_yakuhai_pair(C, P).` in `score.m`. | `all_sequences(Groups),` / `pair_fu(Pair, Seat, Round) = 0,` / `Wait = wait_ryanmen` in the closed-hand branch of `Pinfu` in `eval_standard_yaku`. |
| Pinfu tsumo fu | `( if pinfu(C, I), Tsumo = yes then` followed by `Fu = 20` in `score.m`. | `( if HasPinfu = yes, By = tsumo then` followed by `Fu = 20` in `compute_fu`. |
| Riichi ankan | `K = Drawn,` then `Before = wait_kinds(After, N + 1).` in the `semidet` predicate `riichi_kan_keeps_waits` in `legal.m`. | `K = DrawTile ^ kind,` and `WaitsBefore = WaitsAfter` in the ankan candidate predicate in `legal.m`. |

Opus uses `bag(kind)` where it matters most. The `nondet` `sets` predicate takes the smallest tile with `bag.remove_smallest` and tries removing the balance of a triplet or run. Failure to remove tiles naturally rejects the branch. Another `nondet` predicate gives one solution per applicable yaku. For example, `yaku(C, _, "tanyao", 1) :- all_kinds_are(C, is_simple).` The scorer collects solutions at the boundary. The `in` and `out` modes state which terms are known and the determinism declarations distinguish candidate enumeration, yes/no rules, and one-result evaluation. Opus uses `set(kind)` for wait equality and `set(tile)` for deduplicating physical actions, although its kuikae membership check uses a one- or two-element list. Its kuikae code follows the adjacency wording with `offset(X, 1, Y)`. Agy uses a real set for forbidden kinds, derived from the endpoints of the sorted chi, and shares it across both uses.

Both type-separate kinds and physical tiles, concealed decomposition groups and input melds, and scored interpretations. Opus’s `kind(suit, int)` leaves more to convention than Agy’s separately constructed numbered kinds, winds and dragons. Opus uses a resolved `mentsu` with concealment, and Agy uses constructors for the resolved sequence, triplet and kan; neither preserves meld provenance as part of that scoring distinction. Agy also uses bags for indicator multiplicity and for availability. Both sensibly move the hot shanten inner search into count profiles. Agy uses nondeterminism in decomposition and interpretation, then hand-assembles lists of yaku from conditionals. That lists the rules locally, but obscures the semidet-versus-nondet composition that makes Opus’s score predicates easier to extend. Agy’s fixed profile combination has more explicit index and accumulator plumbing.

Both accepted the valid ankan probe. I found no further valid-game mismatch in the probes I ran. Both silently wrapped the extreme-honba probe. Opus’s ankan-rob path relies on the kokushi predicate’s 14-tile requirement and valid request lengths to exclude melded hands. Agy tests the no-meld condition directly. Opus’s notes read like a working record with concrete failed approaches, including the non-canonical comparison that affected determinism, ambiguity around `pair.-/2`, and an unsuccessful attempt to speed up memo lookup before changing the search. Agy records four failing builds, including clause scope in modes and the expected but missing `char.digit_to_int/2` API, then a clean corpus and a measured waits rewrite. These are individually credible accounts of substantial toolchain learning. The measured Agy advantage on waits (14.9k vs 3.7k req/s) is real on this workload. I would keep Opus for its rule representation and port the factor reuse rather than carry the more verbose scorer.

**Before judging:** reuse unchanged suit profiles across draw candidates, recognize complete shapes directly when checking tenpai waits, unify the value-pair predicate with pair-fu accounting where practical, and validate request context before calling the pure core. Reproduce the clean build in the deployment grade.

### Python · keep Opus

| Rule | Opus | Agy |
|---|---|---|
| Pinfu | `@yaku("pinfu", closed=1)` over a named predicate in `yaku.py`; its return checks four sequences, a non-value pair and `w.wait is Wait.RYANMEN`. | `("pinfu", lambda v: 1 if _is_pinfu(v) else 0),` in `mjlib/yaku.py`; the helper checks menzen, ryanmen, the pair and all-sequence sets. |
| Pinfu tsumo fu | `if is_pinfu and w.tsumo:` followed by `return 20` in `scoring.py`. | `if has_pinfu and v.by == "tsumo":` followed by `return 20` in `mjlib/yaku.py`. |
| Riichi ankan | `if draw.kind != k:` followed by `return False`; then `return before == H.structural_waits(after_counts, len(s.melds) + 1)` in `legal.py`. | `if full_counts[dk] == 4:` with `dk` taken from the draw; then `if b_sh == 0 and a_sh == 0 and b_waits == a_waits:` in `mjlib/legal.py`. |

Opus’s generator, immutable tile tuple, decorated rules and memoized suit search are natural Python. The named functions put eligibility and han beside the rule name. Its `kuikae` helper takes the used tiles or `None` for pon, compares adjacent ranks, and returns a kind set used for both filtering discards and rejecting dead-end calls. Agy likewise shares its helper, expressing the end constraint with `meld_base` and rank arithmetic. Agy’s explicit distinction between decomposition tuples and resolved `HandSet` values is stronger than Opus’s shared `Group(shape, kind, open)` with an openness default. Both convert parsed melds to groups into a separate interpretation (`Win` or `HandView`). Both kind aliases are plain integers, and neither annotation scheme establishes count-vector length, legal ranks, or the connection between form and available fields. Opus handles shared yaku through one registry. Agy’s chiitoi branch repeats several rules from the standard path, including situational yaku and flushes, creating two sites to change.

Both accepted the valid ankan probe and produced exact integer payments on extreme honba. I found no independent valid-game mismatch between them in the probes. The multiple-trigger request below is accepted by both. Opus’s notes claim an initial clean run and record the incremental cleanup and an additional 20,000-hand shape/shanten consistency check. Agy also claims a first-run pass and records compilation, timing, and its cache choice. Both histories are plausible. Opus gives more detail about verification outside the corpus. Neither ran a static type checker. Agy bought measurable speed in several ops through the more specialized profile code, but its extra score plumbing increases the maintenance cost of adding rules.

**Before judging:** typecheck the library, give kind indices and score variants explicit boundaries, validate legal triggers, pass a typed win method and flags from the parser, and benchmark cache memory in a long-lived worker. Keep the generator and single rule registry.

| Rule | Opus | Agy |
|---|---|---|
| Pinfu | `closedOnly "pinfu" 1 $ stdW $ \w gs ->` followed by `length (runs gs) == 4 && not (any (isValuePair w) (pairKind gs)) && waitOf w == Just Ryanmen` in `Score.hs`. | `ykPinfu ctx (StandardShape p ms wt)` with guards `scIsClosed ctx`, `all ((== Seq) . mKind) ms`, `wt == Ryanmen` and `pairFu (srSeat (scReq ctx)) (srRound (scReq ctx)) p == 0`. |

Both use sum types, guards, and list comprehensions naturally. Opus’s list of pure moves plus a scoped strict State memo is concise. Its shared `Group` with an openness flag is used both in decomposition and scoring. The `Reading` sum type does distinguish interpretation from raw groups, although its standard list includes the pair by convention. Agy’s `Decomp` and `HandShape` give the pair its own field and distinguish `CGroup` from `Mentsu`, a better boundary. Its shared `GroupKind` still admits a concealed kan or pair in a list intended for sequences and triplets. Both distinguish kind and exact tile via a type, and both represent open/closed meld categories explicitly at input. Agy’s unboxed counts and strict scoring fields improve hot paths at the cost of more index plumbing. Opus’s `suji` helper expresses the adjacent used tiles as a list pattern. Agy expresses the same logic by matching a sorted three-kind chi with guards and centralizes the entire forbidden-list construction.

Both accepted the valid ankan probe. Agy reads strict `BS.getContents` before processing requests. In an interactive pipe I wrote and flushed `probe agari hand=11223344556677m melds=-`; Agy did not answer until EOF, while Opus answered with stdin open. Batch counts hide that integration issue. Both wrap the extreme-honba arithmetic. Opus accepts the multiple-trigger probe whereas Agy returns `error=bad_legal_event`. Their logs look like working records. Opus shows an IO/plain-value type mismatch, partial-function and shadowing warnings, and a detailed performance progression from 60 waits/s to approximately 3,500 after pruning repeated work, memoizing, and reusing unchanged suits. Agy records a constructor arity error, integer defaulting, partial-function warnings, and the same five corpus-detected kokushi failures as Swift Agy. The overlap identifies a common shape-check mistake. It gives no evidence of answer hard-coding.

**Before judging:** give Opus distinct decomposition and scoring group types and make the pair explicit, use completion-based structural waits in the kan predicate, tighten request validation, remove partial helpers from reachable paths, and profile strict counts and memo allocation under bot workloads. Agy’s `Decomp` and `HandShape` are a useful starting point for the type split.

### Runner boundary probes

These are out-of-corpus boundary tests, independent of the valid Swift Opus riichi-ankan failure.

```text
bad score hand=123456789m123p1z melds=- win=1z by=ron honba=9223372036854775807
bad legal hand=123456789m11p melds=c456s called=c456s took=5s draw=1p
```

For the first request, both Swift release binaries terminated with a trap. Both Haskell and both Mercury binaries reported `pay=ron:3600 total=3600`, consistent with wrapped fixed-width arithmetic. Both Python entries computed the exact large payment. The CLI should either reject out-of-domain honba cleanly or check the arithmetic. For the second request, the format requires exactly one legal trigger. Haskell Agy returned an error. The other seven processed one trigger, silently ignoring the conflict. That supports validating the transition at the parser even when the core uses a discriminated trigger type. Apart from Haskell Agy’s strict whole-input read, delayed output observed on some pipes may just be buffering. Persistent clients need an explicit flush policy.

## Part B · Language ranking for the full engine

I rank for a native engine serving repeated in-process bot calls, a typed round state machine and mjai JSON boundary, with a web client that can initially use the engine over a protocol. I give weight to the maintainer’s preference for Mercury and dislike of Python. If running the exact engine inside a browser is a launch requirement, I would weight the toolchain evidence more heavily.

| Rank | Language | Engine fit and measured cost |
|---|---|---|
| 1 | **Swift** | Sum types and value semantics fit a state machine with variants for draw, response collection, kan replacement and settlement. Exhaustive switches catch missing cases and Swift checked the tile/shape distinctions and closure sendability. The compiler still accepted a bad cache key, potentially invalid ranks and unchecked input to trapping arithmetic. With the same coordinator setup, the two reviewed entries reached 38–40k waits/s and 78–155k score/s. Agy combines fixed-size counts with a different scorer and shanten implementation. The measurements cannot isolate the cause of its scoring lead. Opus reached similar waits throughput with arrays and memoization. The range in legal throughput, 19–31k across the two reviewed entries and 67k for the entry I did not read, is evidence that algorithm and implementation choice matter more than any one result. SwiftPM and Foundation JSON coding give a direct native route. Swift documents a Wasm SDK and JavaScript interop for the browser. Pin the toolchain if the engine uses Agy’s newer inline storage features. [Swift Wasm guide](https://docs.swift.org/latest/documentation/wasmguide/) |
| 2 | **Mercury** | The clearest expression of rule alternatives. A semidet predicate can decide whether a particular transition is valid, a nondet predicate can enumerate call or win candidates, and a det predicate can resolve a validated event into the next round state. Modes and determinism check instantiation and solution cardinality and can constrain IO state threading. They leave rule completeness, payments and tie ordering to tests and domain modeling. Both reviewed entries reached about 93–95k score/s, and unchanged suit-profile reuse made waits range from 3.7k to 14.9k. Opus’s first implementation and failed optimization show that logical clarity can coexist with an expensive search. The maintainer’s familiarity pays off in the core. Agents needed several cycles on mode errors, compiler APIs and syntax, and the project needs a pinned compiler grade and an mjai JSON integration. The documented native C back ends support a separate web client via a service. An in-browser engine would require proving that the runtime and chosen grade can be ported to the browser; emitted C alone does not establish that. [Mercury compiler back ends](https://mercurylang.org/about/backends.html) |
| 3 | **Haskell** | Pure transitions, sum types, and pattern matching fit round flow and replay especially well. List comprehensions express candidate enumeration succinctly, and the type checker caught mixed IO/pure results and incorrect constructor arity. Build with exhaustiveness and partial-function warnings for this engine. Types alone leave list cardinalities, array bounds, arithmetic and protocol buffering open. Opus’s concise search still needed substantial profiling and algorithm changes for waits. Agy nearly doubled agari throughput (119k versus 63k) and led at score (90k versus 53k). Both waits implementations stayed around 4k req/s. A real project can add JSON and package tooling beyond the boot-only restriction here. A browser port has a documented GHC Wasm route requiring a cross compiler and browser/WASI integration. This option becomes more attractive if the maintainer wants pure functional transitions and is willing to own strictness and deployment. [GHC WebAssembly backend guide](https://ghc.gitlab.haskell.org/ghc/doc/users_guide/wasm.html) |
| 4 | **Python** | Generators, dataclasses, and named rule functions supported the lowest reported iteration friction. The standard JSON module and easy local invocation suit a replay or protocol tool. Byte compilation and import checking established little about state transitions. A third-party type checker would help, with deliberate changes to model tile kinds and phase variants. Both implementations used cached suit profiles, yet scored about 21–30k requests/s and handled 4.1–5.7k waits/s. Startup lowers the published rates, particularly on small files, and the remaining repeated Python calls still matter in bot loops. Native hot-path work would split ownership across languages if it became necessary. Python works as a backend for a browser client, and in-browser Python entails packaging a runtime and working within its available platform APIs. Given the maintainer’s preference, I would keep Python for supporting tools and validation. [Python standard-library platform notes](https://docs.python.org/3/library/intro.html) |

For the full game, I would keep the state transition and scoring APIs independent of stdin, string action formatting, UI, and bot policy. A round phase type should carry only data valid in that phase, and simultaneous response collection should feed a single resolution step. Keep the JSON adapter at the edge and build replay tests for multi-ron, furiten, ippatsu cancellation and kan-dora timing. Those transitions were outside the shootout, and testing them is where compiler-enforced state boundaries would make the biggest difference.

The coordinator rates include process startup and line processing on one Apple silicon machine. Differences below roughly 30% are noise under that protocol. Large gaps are informative about these entries, but the benchmark cannot tell us the in-process cost of a mixed bot workload, long-run memo memory, parallel scaling, or browser package size. The logs are self-reports from two agents per language, with different optimization effort. They support a judgment about where the agents stumbled, especially Mercury modes, Swift concurrency diagnostics, Haskell strictness and shape mistakes, and Python’s lack of static feedback. They do not establish relative engineering time for the full game. I did not build a JSON adapter, port an entry to a browser, or benchmark persistent bot calls. Mercury could move into first place if the deployment stays server-side and the chosen grade and wait-path optimization hold up in the bot workload.
